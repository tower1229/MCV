# Canonical Device Skill Store is an MCV resource layout

On macOS, `deploy.useSymlinks: true` materializes each selected Canonical Skill package once in the Canonical Device Skill Store and projects that package to verified IDE Skill Surfaces. The Store currently resolves to the ecosystem-standard `~/.agents/skills/` path, which is also Codex's conventional Agent Skills location, but Codex does not own the Store lifecycle. Materialization remains required while any enabled verified Surface needs the package.

IDE Adapters declare one or more Skill Surfaces with independent native destinations and independent managed-link capability based on real loader evidence. Gemini remains one user-facing target with two Surfaces: Gemini CLI (`~/.gemini/skills/`) and Antigravity (`~/.gemini/config/skills/`). Sharing part of `~/.gemini/` does not make them share a Skills root or inherit each other's link policy. The centralized Deploy layout policy decides physical materialization, per-package projection, copy fallback, ordering, preconditions, backup, and rollback. No Adapter links an entire Skills root or absorbs unowned or IDE-exclusive packages.

The public Deploy Plan/Apply contract remains the safety seam. Plan and Result distinguish physical materialization, managed-link projection, copy projection, topology migration, and an already satisfied projection. Skill projection changes use `owner: "ide"`, one of the three Adapter IDs in `ide`, and the exact loader Surface in `surface`; Canonical Store changes use `owner: "canonical-store"` without either field. An existing physical Skill copy whose package content exactly matches Canonical may be offered as an unselected topology-migration candidate; divergent copies and external links are preserved. Apply regenerates the Plan, revalidates content and link topology, verifies materialized bytes before activating a projection, backs up enough node metadata to restore directories or symbolic links exactly, and rolls attempted content and link mutations back in reverse order after failure.

Store package ownership is established only when MCV successfully materializes a package and records it in `managedSkillLayout.packages`. A missing package may be materialized. A recorded package may be updated under the normal backup and rollback contract. An unrecorded package that exactly matches Canonical is preserved and reused as an external physical source, while only MCV-created projection links enter managed state. Any unrecorded package with different content, extra files, unverifiable links, or unsafe topology blocks Deploy before Store or projection writes. Deleting a recorded Store package is package-level content Drift; replacing it with a same-content external link is topology Drift. Neither case is reported as unchanged or duplicated as projection Drift. Exact external Store packages carry independent content and topology preconditions through Plan and Apply, even though they do not produce materialization changes.

When links are disabled or loader support is unverified for a Surface, MCV uses physical copies for that Surface without forcing link-capable Surfaces to abandon managed links. An already correct link is preserved rather than replaced with a directory. Windows remains copy-only in this decision; existing junctions are detected and grouped without write-through.

Capture treats device projection links as topology rather than portable package content. Several IDE Skill projections that resolve to the same verified physical package produce one Canonical Skill candidate, one sanitized preview, and one set of summary counts. Capture records contributing Surfaces on that candidate without copying projection links into `common/skills/`. Symbolic links embedded inside the physical Skill package remain rejected by the portable-package safety rule. A projection is managed only when its path, expected target, physical identity, and topology hash all match its `managedSkillLayout.projections` record; merely pointing a hand-created link at the Store never grants MCV ownership. A change to link topology or physical identity between Capture Plan review and Apply invalidates the active Plan before Repository writes.
